# Architectural / Resource-Model Comparison with Mixture-of-Experts

The framework selects an initial model for a whole query and may escalate between separate models. Internal MoE selects experts within transformer layers for individual tokens. These operate at different levels and can coexist: query routing here already selects MoE models at tiers 2 and 3.

OpenAI's [official GPT-OSS model card](https://deploymentsafety.openai.com/gpt-oss) identifies both models as MoE: GPT-OSS-20B has 20.9B total / 3.6B active parameters and GPT-OSS-120B has 116.8B total / 5.1B active parameters per token forward pass. These are published architectural values, not measurements from this repository. [Groq model documentation](https://console.groq.com/docs/models) documents hosted access. Successful calls and the saved free-plan cost basis establish access in this environment at collection time; all three API health checks also passed before the amended concise-format cohort. This does not guarantee future availability.

The smallest fair service-level experiment already exists: four identical held-out queries, four controllers, frozen policies, shared generation prompts/output budgets/tool rules, and Always-Strongest starting at GPT-OSS-120B. No additional MoE download or API experiment is needed. Results compare an adaptive service with a fixed MoE-backed service under the common framework policy. They do **not** compare adaptive routing against an isolated MoE algorithm or dense versus sparse architectures. Always-Strongest is not a bare-model baseline; shared tooling can add calls on other queries.

Empirically comparable: reported input/output/total tokens, whole-trajectory active/wall service latency, API calls, rubric quality, selection shares and tool rates. Tokens are provider-tokenizer-dependent resource proxies; output/reasoning accounting differs across providers. Whole-trajectory totals include judging and escalation when present. No such extra calls occurred in this held-out sample.

Not measurable here: expert routing traces, utilization, FLOPs, energy, hardware memory, compute time isolated from serving/network, or paid-cost savings. Do not multiply active parameters by API tokens and call the result measured computation. Attention, prefill/decode, expert scheduling, quantization, batching and tokenizer differences prevent that inference. Gemini's internal architecture/active parameter count is unspecified in this analysis. INR 0 is the recorded user-confirmed free-plan monetary charge, not zero computation.

The empirical table and interpretation are in [performance-analysis.md](performance-analysis.md). Architectural specifications above are literature/background; tokens/latency/grades are recorded experimental evidence; means/reductions are derived statistics. The two forms of conditional computation are complementary; these results cannot establish which architecture is superior.
